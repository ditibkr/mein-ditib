1. AUSGANGSLAGE (IST-ZUSTAND)
================================================================================

Es existieren zwei Laravel-Projekte parallel:

A) vereinsportal/ — Monolith, sehr weit fortgeschritten
   - Laravel 11 + Filament 3.3
   - 42 Models, 72 Migrationen, 30 Filament Resources
   - 21 Services, 8 Jobs
   - Umfang: Mitglieder, Kassenbuch, SEPA, Spenden, WhatsApp, Kurse,
     Dokumente, Inventar, Meetings, FinTS-Banking, PayPal, Paperless-DMS
   - KEINE Modulstruktur (alles in app/)
   - KEIN nwidart/laravel-modules

B) mein-ditib/ — Sauber, modular vorbereitet, wenig Features
   - Laravel 12 + Filament 3.0
   - 7 Models, 10 Migrationen, 3 Filament Resources
   - 4 Services, 1 Job
   - nwidart/laravel-modules v13 bereits installiert (aber nicht genutzt)
   - Sanctum API, Spatie Activitylog, Filament Shield
   - Docker-Setup mit ./src Volume-Mount, proxy-network vorhanden


2. ZIEL: WAS BEDEUTET "OPTIONAL BUCHBAR"?
================================================================================

Jeder Verein, der das Portal nutzt, soll wählen können, welche Module er
aktiviert. Beispiel:

  Verein A (klein):      Core + Mitglieder + Kommunikation
  Verein B (mittel):     Core + Mitglieder + Kassenbuch + SEPA + Kommunikation
  Verein C (vollständig): Alle Module

Das erfordert technisch:
  - Modul-Registrierung in der Datenbank (welche Module sind aktiv)
  - Filament lädt nur die Resources aktiver Module
  - Migrationen nur für aktive Module
  - Rollen/Rechte pro Modul
  - Optional: Abrechnungslogik (SaaS-Billing, hier zunächst manuell)

4. EMPFOHLENER ANSATZ: HYBRID (PORTING)
================================================================================

NICHT empfohlen: Das vereinsportal nachträglich modularisieren.
Begründung: 72 Migrationen und 42 stark verzahnte Models umzustrukturieren
birgt hohes Bruchrisiko. Laravel 11 → 12 Migration wäre parallel nötig.

EMPFOHLEN: mein-ditib als saubere modular Basis verwenden,
           vereinsportal-Code als Referenz Modul für Modul portieren.

Vorteile dieses Ansatzes:
  + Laravel 12 (längster Support-Zeitraum)
  + nwidart-Struktur von Anfang an sauber
  + Jedes Modul kann einzeln entwickelt und getestet werden
  + vereinsportal bleibt als Produktionssystem stabil (kein Bruchrisiko)
  + Porting ist schneller als Neuimplementierung (Logik bereits bekannt)

6. TECHNISCHE UMSETZUNG DES AKTIVIERUNGSSYSTEMS
================================================================================

6.1 Datenbank-Tabelle:
  CREATE TABLE module_activations (
    id, instance_id, module_name, active, activated_at, deactivated_at
  );

6.2 Basis-Service-Provider pro Modul (Muster):
  class MitgliederServiceProvider extends ServiceProvider {
    public function boot(): void {
      if (!ModuleManager::isActive('Mitglieder')) return;
      Filament::registerResources([MitgliedResource::class, ...]);
      $this->loadMigrationsFrom(__DIR__.'/../database/migrations');
    }
  }

6.3 nwidart/laravel-modules kümmert sich um:
  - Autoloading der Module
  - Separate Migrations pro Modul
  - Eigene Routes, Views, Translations pro Modul
  - php artisan module:make ModuleName

6.4 Filament-Integration:
  Filament 3 unterstützt die Registrierung von Resources zur Laufzeit
  via Panel::registerResources() im ServiceProvider — genau das nutzen wir.

8. RISIKEN UND HERAUSFORDERUNGEN
================================================================================

R1: Abhängigkeiten zwischen Modulen
    Wenn Kassenbuch auf Mitglieder verweist, braucht es Interfaces oder Events.
    Lösung: Laravel Events/Listeners für lose Kopplung + optionale Relations.

R2: Migrations-Reihenfolge bei aktivierten/deaktivierten Modulen
    Wenn Modul B später aktiviert wird, müssen seine Migrationen funktionieren
    auch wenn Modul A schon lange läuft.
    Lösung: Jedes Modul pflegt eigene Migrations mit sauberen FK-Checks.

R3: vereinsportal läuft produktiv
    Während mein-ditib aufgebaut wird, läuft vereinsportal weiter.
    Kein Migrations-Druck, kein Zeitdruck durch Produktionsausfall.
    Das ist ein Vorteil dieses Ansatzes.

R4: Laravel 11 → 12 Unterschiede beim Porting
    Gering: Beide nutzen Filament 3. Syntax-Unterschiede minimal.
    Größter Unterschied: bootstrap/app.php Middleware-API (bereits gelöst).

R5: nwidart/laravel-modules v13 API
    Version 13 hat Breaking Changes gegenüber v11/v12.
    Muss einmalig gründlich eingerichtet werden.
